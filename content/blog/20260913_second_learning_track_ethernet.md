## Same rule, new domain

With RX digital bring-up done and ported into permanent firmware, a new front opened on this project: replace the UART configuration console with UDP, and eventually stream RX samples over Ethernet too. I wanted the same deal I'd made for myself on the RTL side of this project, stated directly to Claude:

> "I wish to make the learning on this interface, I did it before on FPGA, so I want to be followed on the sw part too."

Same collaboration model, transplanted from SystemVerilog into bare-metal C: I write the GEM0/PHY/MDIO/Ethernet driver logic myself, Claude reviews it, explains register semantics when I ask, and handles the mechanical plumbing — build system changes, UART console wiring — without touching the driver logic itself. Seeing that pattern re-form cleanly around a completely different domain, rather than being some one-off RTL quirk, told me it's actually how I want to work on this project generally.

## Getting the PHY identity right before writing a line of driver code

A real schematic check nailed down the physical layer chip as a Realtek RTL8211F-CG, RGMII, 25MHz reference clock — and resolved a near-miss along the way. `RSET` and `PHYRSTB` are separate, easily-confused pins on this part, and only one of them is actually a reset line; the other is just the standard bias-setting resistor. Worth the extra minute checking the datasheet rather than assuming from the name alone, because getting that backwards would have meant "fixing" a reset line that was never broken.

Before any code got written, I put together a structured roadmap document with the driver bring-up broken into steps, agreed as the scaffold before touching anything.

## The same mistake, predicted and then made anyway

The first real register-packing work — GEM0's clock setup and core control registers, sourced from a cheat sheet a separate Claude instance had digested from the datasheet and the Zynq TRM, explicitly treated as unverified rather than as ground truth — produced a genuinely human moment. I spotted a register bit labeled `100`, meaning "100Mbps," and immediately flagged it as a naming trap: it's not a 3-bit binary pattern, it's a decimal label that happens to look like one. One function later, in my own next draft, I fell into the identical trap: a bit named `1000` — gigabit enable, a single bit at position 10 — got encoded as `0x8u << 10`, landing on bit 13 instead of bit 10. Gigabit mode never actually got enabled. Same category of mistake, predicted in the abstract, made concretely one field over.

A more consequential bug sat right next to it: an early setup function enabled TX/RX before any DMA descriptor ring existed. Not just premature — a genuine hazard, since GEM's DMA engine would write an incoming frame, like an ARP broadcast arriving unprompted the moment a cable gets plugged in, to whatever garbage address the base register happened to hold at reset. On this bare-metal project, that garbage address is the exception vector table at address zero. Both issues got scoped back out until the ring actually existed.

A smaller thing, but worth keeping: a TODO I'd left myself with a guessed comment — "is CPU freq 100MHz? so divisor is 40?" — got resolved not from memory but by grepping the project's own generated `ps7_parameters.xml` for the real answer. CPU_1x is 133.333MHz on this board. Small demonstration of checking the artifact instead of trusting even your own throwaway guess.

## Proving MDIO works before a driver function existed

Rather than writing `phy_mdio_read()` first and hoping it worked, I added one more raw device to the UART register console I already had — direct byte-offset read/write into GEM0's register space — and that alone was enough to hand-drive a complete MDIO transaction from a PC: poll idle, write a hand-packed 32-bit command word, poll idle again, read the result. Every command word was computed by hand from the register's bit-field table, not generated by any code.

The result: PHY register 2 read `0x001C`, register 3 read `0xC916` — together, PHY ID `0x001CC916`, an exact match for the RTL8211F's known silicon ID, at MDIO address 0. I picked identity registers over a link-status bit specifically because of something from an earlier project:

> "From what I remember when I implemented something similar on an Arty A7 100T, the MDIO replies if called with it's name. Hence a read only register read could be proof of operation."

One test validated five separate things at once: clock gating, the management-port enable bit, a guessed MDIO clock divider, the hand-packed field layout, and PHY addressing — stronger evidence than the roadmap's own planned milestone, a link-bit toggle, precisely because a static ID match rules out reading plausible-looking garbage.

While writing a note on sweeping other PHY addresses, I caught myself making a hex-addition slip — `0x680A0000` instead of the correct `0x608A0000`, two nibbles transposed — by re-deriving the value bit by bit instead of trusting my first pass. Small, but it's exactly the kind of error that would've quietly sent a future test to the wrong address.

The link-status check that followed produced a genuine textbook moment: bit 2 (Link Status) read `0` on the very first poll after plugging the cable in — indistinguishable from failure — but a second consecutive read showed `1`. That's a documented IEEE 802.3 Clause-22 quirk: Link Status latches low and clamps through one read after any link-down event, only live starting from the read after that. I confirmed it was expected rather than a bug because a different, non-latching status bit flipped correctly on the very first read, every time.

## Writing the real driver, and the mistakes that came with it

Once the mechanism was proven by hand, I wrote the actual functions on top of it: `phy_query_mdio()`, `phy_write_mdio()`, `phy_get_rtl_identifier()`. The first draft had a bug I'd already half-caught in my own comment: `while (GEM_NWSR != 0x04)`, an exact-equality check against a value my own hardware testing earlier that same day had already proven never occurs — the register reads `0x06`. Run as written, that loop would hang forever, provably, using data I'd already collected myself. A quieter bug sat right beside it: `&&` where `&` was intended, logical AND instead of bitwise — which doesn't crash or hang, it just silently produces a plausible-looking wrong number, arguably the more dangerous of the two failure modes.

A refactor fixed both and introduced a fresh one: the left-shift placing an MDIO command word into the correct half of the register got dropped when the logic moved from a direct write into a reusable function. Caught in review — except my correction was quick and I was right:

> "no? I added the left shift by 16"

The reviewer had been looking at a stale copy of the file, not my actual code. The version that finally ran end to end wired `phy_get_rtl_identifier()` to run automatically at boot, printing its result over UART before the interactive console even started. A fresh reload produced a clean `00 1c c9 16` — the same PHY ID as the manual test, now reached entirely through my own C code.

## A small process mistake, on the other side

Asked to create a new reference file for the MDIO test procedure, Claude searched for it, found nothing, and wrote a fresh file — except the file already existed, holding my own earlier SPI bring-up notes, and there's no version control in this project's private notes folder to recover them from. Silently gone. I caught it immediately:

> "you keep completelly ovewriting my bring_up_uart.txt, it had the old SPI instruction... unless indicated a full wipe out of the file, just append the new information at the end."

Acknowledged directly rather than explained away, and it became a standing rule for the rest of the session: append, don't overwrite, for any file I also edit by hand. Worth keeping in the record rather than cutting for flattery — it's the same "show the wrong turns" approach the rest of this project's story already commits to, just pointed at the assistant instead of me for once.

This session proved the collaboration pattern generalizes past RTL. What it didn't prepare me for was the next day, which turned into the single longest, most eventful stretch of the whole project — TX finally worked, and then things got a lot more interesting. That's next.
